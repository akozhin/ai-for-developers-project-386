# ADR-004: Один Docker-образ, один процесс на `PORT`, деплой на Render

> **Статус:** Предложено · **Дата:** 2026-10-09

## Контекст

Приложение нужно упаковать в Docker и опубликовать. Требования шага: `Dockerfile` в корне репозитория, контейнер стартует автоматически, приложение слушает порт из переменной `PORT` (и при деплое, и в автоматической проверке), у сервиса есть публичная ссылка, она добавлена в репозиторий. Приложение состоит из backend (FastAPI), frontend (Next.js) и PostgreSQL. В проверке контейнер, вероятно, запускается без БД, поэтому приложение не должно падать на старте без неё.

Проверено по документации Render и опытным путём:

- Render MCP умеет создавать веб-сервис из репозитория с `runtime: docker` (`dockerfilePath`, `dockerContext`), создавать и опрашивать Postgres, запускать деплой, читать логи и метрики. **Не умеет** разворачивать готовые образы из реестра, удалять ресурсы и менять масштабирование; в параметрах создания сервиса платные планы (`starter` и выше).
- Для сервиса и БД бесплатный план Render доступен через Blueprint (`render.yaml`) или панель; бесплатный веб-сервис засыпает без трафика, бесплатная БД удаляется через 30 дней.
- Frontend собирается как статический экспорт (`output: "export"`): проверено, обе страницы (`/`, `/admin`) экспортируются, итог 1,2 МБ. Для этого нужно убрать `cacheComponents` и `partialPrefetching` (PPR несовместим с экспортом); `use cache` в коде не используется.

## Рассмотренные варианты

1. **Один образ, два процесса** (Next.js `standalone` + uvicorn, Next проксирует `/api/v1/*`). Нужен менеджер процессов, два порта, прокси; больше точек отказа.
2. **Два сервиса и два Dockerfile.** Противоречит требованию одного `Dockerfile` в корне и усложняет проверку.
3. **Один образ, один процесс (выбран):** FastAPI отдаёт и API, и собранный frontend (статический экспорт Next.js) с одного origin. Прокси и CORS не нужны, один порт `PORT`.

## Решение

- **`Dockerfile` в корне, многоэтапный:** (1) Node — установка зависимостей, `make generate`-совместимая сборка frontend в статику `frontend/out`; (2) Python — зависимости backend через `uv`, копирование кода и `frontend/out`; непривилегированный пользователь; `EXPOSE`/запуск по `PORT`.
- **Запуск:** `uvicorn app.main:app --host 0.0.0.0 --port ${PORT}`; `PORT` по умолчанию, если не задан, — 8000. Приложение стартует без БД (подключение ленивое): `/health` отвечает всегда, маршруты с БД вернут ошибку, пока БД недоступна.
- **Отдача frontend:** FastAPI монтирует `frontend/out` после API-маршрутов; `/admin` отдаётся из `admin.html`; неизвестные пути — `404` в формате ошибок API для `/api/*` и страница 404 для остальных.
- **Миграции и начальные данные — флагами окружения**, а не всегда: `RUN_MIGRATIONS=true` — перед стартом `alembic upgrade head` (при ошибке контейнер падает, чтобы деплой не считался успешным); `SEED_ON_START=true` — после старта идемпотентно создаются типы 30 и 60 минут. По умолчанию оба выключены, поэтому автоматическая проверка без БД проходит.
- **`DATABASE_URL`:** принимает форматы `postgres://` и `postgresql://` (так их отдаёт Render) и приводит к `postgresql+asyncpg://`.
- **Конфигурация frontend:** `rewrites` остаются только для разработки (в экспортной сборке не поддерживаются), `cacheComponents` и `partialPrefetching` удаляются как неиспользуемые.
- **Healthcheck:** `GET /health`.
- **Render:** `render.yaml` (Blueprint) в корне описывает веб-сервис `runtime: docker` и базу Postgres, `healthCheckPath: /health`, переменные `RUN_MIGRATIONS=true`, `SEED_ON_START=true`, `DATABASE_URL` из БД, `OWNER_NAME`/`OWNER_TIMEZONE`; секреты (если понадобятся, например `AI_API_KEY`) задаются в панели, не в репозитории. Render MCP используется агентом для проверки (статус деплоя, логи, метрики), для создания Postgres и сервиса, если выбран платный план. Публичная ссылка записывается в README.
- **Запасной вариант:** Railway (тот же образ, `PORT`, публичный домен), если Render требует оплату или недоступен.

## Последствия

- (+) Один образ и один процесс: проще запуск, проверка и деплой; нет прокси и CORS.
- (+) Образ одинаково запускается локально, в CI и в облаке; без БД стартует и отвечает на `/health`.
- (−) В продакшене нет серверного рендеринга и `use cache`: весь UI клиентский (так уже работает приложение).
- (−) Из конфигурации frontend убираются PPR и Cache Components; вернуть их можно, только перейдя на вариант с процессом Next.js.
- (−) Бесплатный план Render: засыпание сервиса и истечение бесплатной БД через 30 дней; для стабильной работы нужен платный план.
- (−) Секреты в панели Render не версионируются; значения нужно перенести вручную при пересоздании сервиса.
