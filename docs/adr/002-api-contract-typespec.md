# ADR-002: API-контракт описываем в TypeSpec (Design First)

> **Статус:** Принято · **Дата:** 2026-10-09

## Контекст

Приложение делается в подходе Design First: сначала фиксируем поведение и API-контракт, потом раздельно реализуем frontend и backend. Контракт — граница между частями и единый источник правды. Использование TypeSpec — требование задания. Сейчас контракт — черновик в `docs/concept/api-contracts.md`, а frontend держит рукописный тип `EventType` и проверку ответа.

## Рассмотренные варианты

1. **Рукописный OpenAPI (`openapi.yaml`)** — стандарт, много инструментов. Минусы: многословный YAML, повторы схем, легко разойтись с кодом без дисциплины.
2. **Code-first: схема из кода FastAPI** — ноль ручной работы. Минусы: контракт становится побочным продуктом реализации backend, frontend ждёт готового кода, Design First теряет смысл; любое изменение кода молча меняет контракт.
3. **TypeSpec с эмиссией в OpenAPI 3.1 (выбран)** — компактное типизированное описание, из него генерируется OpenAPI. Контракт пишется до кода и проверяется компилятором.

## Решение

- Источник правды — `api/*.tsp` (пакет `api/` с собственным `package.json` на pnpm, `tspconfig.yaml`, эмиттер `@typespec/openapi3`).
- Результат компиляции `api/openapi.yaml` (OpenAPI 3.1) коммитится. Вся цепочка генерации запускается одной командой `make generate` (OpenAPI, затем SDK frontend); `make generate-check` перегенерирует её и падает на расхождении (`git diff --exit-code`), входит в `make ci`. Сгенерированные файлы помечены «не править руками». В `tsp compile` предупреждения считаются ошибками, плюс `tsp format --check`; отдельного линтера спецификации нет.
- **Любое изменение API начинается с TypeSpec**, затем перегенерируется `openapi.yaml`, затем код. В PR правка контракта — отдельным коммитом до реализации.
- **Backend** ничего не генерирует: ни контракт из кода (бессмысленно, контракт уже существует), ни серверные заготовки из контракта (осознанное отступление от учебного задания: типы, маршруты и валидация пишутся руками на FastAPI и Pydantic). Соответствие контракту проверяет Schemathesis в pytest поверх ASGI-приложения. `/docs` и `/openapi.json` FastAPI отдают закоммиченный `api/openapi.yaml`.
- **Frontend**: типизированный SDK (типы и клиент) генерируется из `api/openapi.yaml` инструментом `@hey-api/openapi-ts`, коммитится в отдельный каталог и проверяется на устаревание в CI. Рукописные типы и guard-функции удаляются, MSW-моки типизируются типами SDK.
- Версионирование: путь `/api/v1/...`, `/health` без версии. До первого публичного релиза v1 можно менять несовместимо; после — только через `/api/v2`. `info.version` не связан с версией release-please.

## Последствия

- (+) Контракт появляется раньше кода, frontend и backend разрабатываются независимо.
- (+) Дрейф ловится автоматически: генерация (`generate-check`), типы frontend (CI), ответы backend (Schemathesis).
- (−) Ещё один инструмент (Node-пакет `api/`) и слой генерации; для шести эндпоинтов это оправдано требованием задания.
- (−) Схема FastAPI и Pydantic-модели пишутся отдельно от контракта, а не выводятся из него; расхождения ловит только Schemathesis.
